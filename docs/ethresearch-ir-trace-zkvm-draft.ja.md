# Lean で書いた STF を zkVM で証明する

## 1. TL;DR

リポジトリ: https://github.com/NyxFoundation/verifiable-stf

イーサリアムのロードマップでは、状態遷移関数 (STF) を zkVM 上で証明可能にする方向が議論されている。STF を毎回再実行する代わりに簡潔な ZK 証明だけを検証できれば、ノードのリソース要件は大きく下がり、コンセンサス参加の敷居も低くなる。

このロジックはイーサリアムのセキュリティを語る上で非常に重要であり、将来的に形式検証されるべきだと考えられる。
本投稿では、形式検証済み STF を zkVM 上で証明するアプローチの探索結果を報告する。STF を Lean で記述し、RISC Zero zkVM 内部でその実行の zk 証明を得る方法として 3 つのアプローチを検討した。本投稿が主に掘り下げるのは 3 つ目の IR Trace アプローチである。

| アプローチ | zkVM ゲスト内部で動くもの |
|----------|--------------------------|
| Rust コンパイル → RISC-V | 手書きの Rust 製 STF (ベースライン) |
| Lean コンパイル → RISC-V | STF 全体 + Lean ランタイム + `Init` (初期化だけで ~15M cycles) |
| Lean IR Trace (本投稿の焦点) | ホストが生成した実行トレースを再検証する小さなチェッカ |

IR Trace アプローチでは、バリデータが 1 人だけでもトレースは 7.85 GB になり、実装の入力上限 (~4 GB) を大きく超える。トレースサイズは「バリデータ数によらない固定コスト ~7.81 GB」＋「バリデータ 1 人あたり ~32.7 MB」で増えるため、バリデータ数を減らしても壁は越えられない。

本投稿ではその数値と直面した壁を共有し、トレース圧縮の方向性（および「インタプリト後検証」という設計自体が正しい形なのか）についてフィードバックを募集したい。

本投稿で報告するすべての結果は、以下の 3 つの前提に基づく。後段を読む前にここを押さえてほしい。

1. ホスト側インタプリタは公式 C++ IR インタプリタの独立再実装である。 本投稿で「Lean プログラムを実行した」と言う場合、それは「この独立再実装インタプリタで λRC IR を実行した」という意味であり、公式 C++ インタプリタ ([`ir_interpreter.cpp`](https://github.com/leanprover/lean4/blob/master/src/library/ir_interpreter.cpp)) との bit-for-bit 等価性は確立していない。差異の詳細は「3.1. ホスト側インタプリタ」を参照してほしい。
2. 暗号プリミティブはスタブとして公理化する。 `hashTreeRoot`, `blsVerify` 等は記録済みの結果を guest 側でそのまま受け入れ、再実行しない。
3. 本実装は特定の実行インスタンスを証明するものであり、全入力に対する定理証明ではない。 ある pre-state と block を与えたとき特定の post-state が得られたことを証明する。Lean の型レベルの定理証明とは別物である。

## 2. 動機

形式検証とはコードの正しさを数学的に証明する技術であり、全入力を網羅できるためテストでは到達できないバグクラスを排除できる。Ethereum コンセンサス仕様は、まさに証明支援系で書きたくなる類の成果物だ。

私たちが出発点にした問いは: STF が Lean で書かれているとして、ある pre-state + block から ある post-state が得られたことの、簡潔な ZK 証明をどう得るか？

素直なルートは、その STF を zkVM 内部で走らせることだ。Lean のコンパイラは関数型プログラムを最終的に C ソースコードに出力できる。理論上は、その C を RISC-V 向けに再コンパイルして zkVM のゲストプログラムとして走らせる経路が成立する。

このアプローチは実際に動くが重い。Lean ランタイムと標準ライブラリの初期化（`Init`）だけで、本ベンチマークでは ~15M cycles のコストを支払う。

## 3. IR Trace アプローチ

そこで考えたのが: Lean を RISC-V にコンパイルすること自体を回避できないか？

Lean のコンパイラは C を吐く前に、プログラムを小さな中間表現 (IR) である lambda-RC (λRC) に変換する。この IR はステップ単位で逐次評価できる構造を持つ — `let x := expr; ...` の連なりと `Branch` / `Call` / `Set` 等の基本演算で構成されており、各ステップが「直前の値テーブルから新しい値を 1 つ生成する」形になっている。

これは zkVM の証明フローと自然に噛み合う: zkVM もステップ列を 1 つずつ再実行して最終状態へのコミットメントを得る。ならば IR をホスト側でインタプリトし、各ステップを記録して、zkVM ゲストを言語ランタイム全体ではなく小さなトレースチェッカに縮められないか? それが IR Trace アプローチである。

Lean 自身も同様の発想で、LLVM JIT が使えないプラットフォーム（WebAssembly 等）向けに公式の C++ λRC インタプリタ（[`ir_interpreter.cpp`](https://github.com/leanprover/lean4/blob/master/src/library/ir_interpreter.cpp)）を持っている。しかしこれをそのまま使うことはできなかった。「実行する」だけで、ステップごとの中間値を構造化して記録する機能がないからだ。そこで同じ IR 仕様を Rust で独立再実装し、トレース emit を追加した。

### 3.1. ホスト側インタプリタ

IR Trace のパイプラインは以下のようになる。

```
Lean STF
   │  lambda-RC IR をダンプ  →  ir_program.json
   ▼
ホスト側インタプリタ  ──  入力上で IR をインタプリトし、各ステップを記録  →  trace (bincode)
   ▼
ホスト側ドライバ  ──  IR と入力をハッシュし、{ir_hash, input, trace} を zkVM に渡す
   ▼
zkVM ゲスト  ──  各トレースステップを再検証し、出力ハッシュを commit する
```

「ホスト側インタプリタ」が何であるかを明確にしておく。

Lean 公式の λRC インタプリタ [`ir_interpreter.cpp`](https://github.com/leanprover/lean4/blob/master/src/library/ir_interpreter.cpp) は λRC IR の参照実装だが、本プロジェクトでは直接使えなかった。理由は 2 つある: (1) C++ であり Rust/RISC Zero エコシステムとの統合が難しい、(2) ステップごとの中間値を構造化して記録する機能がなく、トレース emit をゼロから追加する必要がある。

そこで λRC IR 仕様（[`Lean/Compiler/IR/Basic.lean`](https://github.com/leanprover/lean4/blob/master/src/Lean/Compiler/IR/Basic.lean)）を Rust で独立再実装し、トレース emit を組み込んだ。「C++ を Rust に翻訳した」ものではなく、仕様から起こした別実装である。この再実装には 3 つの意図的な差異がある:

1. 参照カウント操作を clone に置き換え。 `Inc` / `Dec` / `Del` 命令は本来 Lean ランタイムの refcount を操作してメモリを管理する。zkVM 上では GC もメモリ再利用も不要なため、これらを値の `clone()` に読み替えた。意味論的には等価だが、clone はメモリを消費する（zkVM ゲストでの検証には影響しない）。

2. in-place 最適化命令（`Reset` / `Reuse`）を省略。 λRC の `Reset` / `Reuse` は refcount が 1 であることを確認してメモリを再利用するコンパイラ最適化である。意味論に影響しないため省略した。

3. `dlsym` ネイティブ dispatch を extern スタブに置き換え。 C++ インタプリタは `blsVerify` や `hashTreeRoot` といった暗号プリミティブを `dlsym` で動的にリンクして呼び出す。Rust 再実装ではこれらを extern スタブとして静的に定義し、記録済みの戻り値を返すだけにした — zkVM ゲスト側での再実行は行わない（詳細は「3.2. ゲストが実際に検査するもの」）。

これらの差異がある以上、本投稿で「Lean プログラムを実行した」と言う場合、それは「この独立再実装インタプリタで λRC IR を実行した」という意味であり、公式 C++ インタプリタとの bit-for-bit 等価性は確立していない。検証集合から外れる演算（`USet` / `SSet` / `SetTag`）については次節で詳述する。

### 3.2. ゲストが実際に検査するもの

トレースは「値テーブル（全中間値のフラットなリスト）」と「ステップのリスト」で構成され、IR プログラム・入力・出力の SHA-256 ハッシュを含むヘッダで包まれている。ゲストはまずこの 3 つのハッシュが一致することを assert し、証明を特定のプログラム + 入力 + 出力に束縛する。

トレースステップは 6 種類の enum で表現される（`ir-trace-common/src/trace_types.rs`）:

```rust
pub enum TraceStep {
    Call      { fn_id: u32, args: Vec<ValueId>, result: ValueId },
    Branch    { scrutinee: ValueId, chosen_tag: u16 },
    PrimResult { op: PrimOp, args: Vec<ValueId>, result: ValueId },
    CtorCreate { tag: u16, fields: Vec<ValueId>, scalar_data: Vec<u8>, result: ValueId },
    ProjResult { obj: ValueId, idx: u16, result: ValueId },
    SetResult  { obj: ValueId, idx: u16, val: ValueId, result: ValueId },
}
```

ゲストの検証器はこれを以下のように再検査する（`methods/guest-ir-trace/src/verifier.rs`, 抜粋）:

```rust
match step {
    TraceStep::PrimResult { op, args, result } => {
        // 演算を再計算し、記録された値テーブルのエントリと照合する
        let computed = eval_primitive(op, &args.iter().map(|id| values[*id as usize].clone()).collect());
        assert_eq!(computed, values[*result as usize]);
    }
    TraceStep::Branch { scrutinee, chosen_tag } => {
        // scrutinee の実際のタグと記録された分岐先が一致することを確認する
        assert_eq!(values[*scrutinee as usize].tag(), *chosen_tag);
    }
    TraceStep::Call { .. } => {
        // ユーザ関数: サブステップとしてトレースにインライン化済み → そちらで検査される
        // extern スタブ (hashTreeRoot, blsVerify 等): 公理として信頼 — 再実行しない
    }
    // CtorCreate / ProjResult / SetResult も同様に assert_eq! で照合
}
```

- `PrimResult` / `CtorCreate` / `ProjResult` / `SetResult` / `Branch`: 値テーブルに対して完全に再検査される。
- `Call`（ユーザ関数）: インライン化されたサブステップが検査されるため、呼び出し自体はパスする。
- `Call`（extern スタブ — `hashTreeRoot`, `blsVerify` 等）: 記録された結果を受け入れ、再実行しない。

現在の被覆ギャップ — in-place ミューテーション: フィールド更新の `Set` 演算は `SetResult` ステップとして記録・再検査される。しかし in-place ミューテーション演算 `USet` / `SSet` / `SetTag` はインタプリタで実行されるがトレースステップを emit しないため、現在は検証の外側に落ちる。ETH2 の証明を意味あるものにするにはこのギャップを塞ぐことが必須だ。なお `USet` / `SSet` / `SetTag` の意味論は公式 C++ インタプリタに実装済みであり、tracing を付加した Rust への移植は難しくない。

何が正確に証明されているか: 証明は IR プログラムハッシュ、入力ハッシュ、出力ハッシュ、そして上記で検査されたトレース意味論を束縛する。公式 C++ インタプリタとの等価性は確立しないし、スタブされた暗号の正しさも確立しない。信頼境界は「extern スタブの集合」と「in-place ミューテーションの被覆ギャップ」で尽きる。

## 4. ベンチマーク結果

測定環境: AMD Ryzen 9 PRO 8945HS (8 コア / 16 スレッド, 最大 5.26 GHz), L2 8 MiB / L3 16 MiB, RAM 64 GiB, Linux 6.18 (Kali)。

注意: 3 つのアプローチは共通のコスト指標を持たない。ホストインタプリタの統計（ステップ数、トレースサイズ）は IR Trace にしか存在せず、zkVM cycle 数はコンパイル系 2 つにしか存在しない。誤解を防ぐため 2 つのバケットに分けて報告する。

### 4.1. トレースサイズ（IR Trace）

V=1,2,3 を直接実測し、V=10・V=100 と照合した:

| V（バリデータ数） | シリアライズ後トレース | トレースステップ | 値テーブル要素 | 出力 |
|---------------:|-----------------:|------------:|--------------------:|-------:|
| 1   | 7.85 GB              | 229,371 | 617,066 | 77,199 B |
| 2   | 7.88 GB              | 230,334 | 619,593 | 77,346 B |
| 3   | 7.91 GB              | 231,308 | 622,147 | 77,493 B |
| 10  | 8.14 GB              | 238,049 | 639,836 | 78,522 B |
| 100 | ≈11.1 GB（推定） | 324,741 | 867,320 | 91,752 B |

（トレースバイト数は V=1,2,3,10 で実測; V=100 はバイトのみ外挿 — 10 GB 超のトレースを計量だけのためにシリアライズするのは割に合わないため。ステップ数と値テーブル要素数は 5 点すべてで実測済み。）

スケーリングの構造: 固定コスト + バリデータ比例コスト。 V=1,2,3 への線形フィットにより、各指標は「バリデータ数によらない固定コスト」と「バリデータ 1 人あたりの追加コスト」に分解できる:

```
シリアライズ後トレース ≈   7.81 GB  +  32.7 MB  × V
トレースステップ       ≈  228,400   +    968    × V
値テーブル要素         ≈  614,500   +  2,540    × V
出力サイズ             ≈   77,052   +    147    × V  (bytes)
```

このフィットの精度は高い: V=10 で 8.14 GB と 238,080 ステップを予測し、V=10・V=100 の出力サイズ（78,522 B, 91,752 B）を完全に再現する。

![シリアライズ後トレースサイズ vs バリデータ数: V=1,2,3,10 の実測点が切片 ~7.81 GB, 傾き ~32.7 MB/validator の直線上に並び、V=100 で ~11 GB に外挿される; 全線が ~4 GB 入力上限をはるかに超えている。](assets/bench-scaling.svg)

このスケーリング構造には 2 つの帰結がある:

- 今すぐ動かせる小さいスケール（V ≤ 100）でも、固定コストが壁になる。 V=10 時点でトレースの ~96% を固定コストが占め、それだけで ~4 GB の入力上限を超えている（V=1 でも 7.85 GB）。バリデータ数を 1 まで減らしても壁は越えられない。
- メインネットスケール（~100 万バリデータ）では比例コストも壁になる。 32.7 MB/validator が TB 台に外挿され、固定コストと合わせて圧縮なしでは到底扱えない。

（V=10→V=100 だけを見ると「1.36×, ほぼ横ばい」と見えた。しかしこれは固定コストの巨大な切片がバリデータ比例コストを覆い隠していたにすぎない。）

実測でもこの壁は確認できる。 本実装の入力パスは `env::write()` を介して `Vec<u8>` を u32 長さ prefix 付きでシリアライズしており、ホスト側で ~4 GB のあたりで `TryFromIntError` に当たる。固定コスト ~7.81 GB だけで既に ~4 GB 上限を超えており、V=1 のトレースでも 7.85 GB に達する。

![シリアライズ後トレースを固定コスト ~7.81 GB（バリデータ数によらない構造的なコスト）とバリデータ比例コストに分解して V=1, V=10, V=100 で表示; 固定コストだけで全バリデータ数において ~4 GB 入力上限を超えている。](assets/bench-trace-size-wall.svg)

なぜ固定コストがこれほど大きいのか? インタプリタはすべての中間値を値テーブルにコピー（clone）して保存する。ETH2 の中間値には大きな `ByteArray`（beacon state は ~78 KB）と深くネストされた `Object` が含まれ、それらの多くがほぼ同じ内容（例えば 1 インデックスだけ変更されたバイト配列が丸ごと新しいコピーになる）である。これらのコピーの大部分は STF のバリデータ数に依存しない骨格部分で発生するため、固定コストが支配的になる。トレース形式を JSON（~15 GB）から bincode に変えても ~1.8× しか縮まなかった — コストは JSON の構文オーバーヘッドではなく、複雑にネストした値のシリアライズ自体に支配されているからだ。バリデータ比例コスト（~32.7 MB/validator）は同じコピー病理がバリデータ状態に適用されたもので、V=1 では無害だがメインネットの ~100 万バリデータでは壊滅的になる。

コンパイル Lean との対比: そちらでは中間値はページングされた zkVM メモリ上に置かれ、シリアライズされることはない。IR Trace はすべての計算をホスト側に外部化し、すべての中間結果をゲストに手渡さなければならない — これが爆発の根本原因である。

![N=10 における IR-trace のステップ構成: PrimResult 42.2%, Call 21.5%, ProjResult 16.7%, Branch 11.4%, CtorCreate 4.6%, SetResult 3.7%（総ステップ 238,049 のうち）。](assets/bench-step-composition.svg)

`PrimResult`（算術演算）はバリデータ比例コストが最も大きい種類のステップで、V が増えるほどシェアが増える（V=1 で 41.3% → V=10 で 42.2% → V=100 で 48.5%）。それ以外はすべて固定コストに支配されている。

### 4.2. コンパイル系との比較

コンパイル系 2 アプローチの STF 出力サイズは V=10 で 78,746 B、V=100 で 91,976 B であり、IR Trace（4.1 の表「出力」列参照）と 224 B 差で一致する。差分はインタプリタ駆動のシリアライザの違いによるもので、STF 自体の発散ではないと考えているが、未調整である。

| アプローチ | cycles (V=10) | seg (V=10) | cycles (V=100) | seg (V=100) |
|----------|--------------|-----------|---------------|------------|
| Rust（コンパイル, ベースライン） | 12,491,509 | 13 | 14,446,747 | 15 |
| Lean（コンパイル, `Init` 込み） | 26,148,291 | 29 | 35,281,299 | 38 |

![zkVM cycles: コンパイル済み Lean vs Rust (V=10, V=100)。Rust はおおよそ Lean の半分の cycle 数。IR Trace の zkVM 検証はトレースサイズによってブロックされており利用不可。](assets/bench-zkvm-cycles.svg)

Lean は Rust の約 2.1× (V=10) ～ 2.4× (V=100) のコストになる。差の大部分は Lean ランタイムと `Init` による固定オーバーヘッド (~15M cycles) であり、STF 本体の実行コストは Rust と大きく変わらない。V=10→V=100 でのスケーリングは Rust が +2.0M cycles、Lean が +9.1M cycles と Lean の方が大きい。

## 5. 既知の制約

これは研究プロトタイプである。健全性に関わるギャップがいくつかあるので再度述べておく:

1. ホスト側インタプリタは公式 C++ λRC インタプリタの独立再実装であり、忠実な移植ではない。 Lean 自身のランタイムとの bit-for-bit 等価性は確立していない。3 つの意図的な差異については「3.1. ホスト側インタプリタ」を参照してほしい。
2. 暗号プリミティブはスタブ化されており信頼される（`hashTreeRoot`, `blsVerify`, …）。上述の通り。
3. in-place ミューテーションのトレース被覆が不完全。 フィールド更新の `Set` 演算は再検査される `SetResult` ステップを emit する。しかし in-place ミューテーション演算 `USet` / `SSet` / `SetTag` はインタプリタで実行されるがトレースステップを emit しないため、現在は検証の外側に落ちる。ETH2 証明を意味あるものにするにはこのギャップを塞ぐことが必須である。
