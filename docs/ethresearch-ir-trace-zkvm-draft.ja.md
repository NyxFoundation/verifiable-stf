# Lean で記述された Ethereum STF を zkVM 上で検証する：IR をインタプリトしトレースを証明するアプローチ

## TL;DR

Ethereum コンセンサスの状態遷移関数 (STF) を Lean 4 で記述し、その実行に対する zk 証明を RISC Zero zkVM 内部で得る方法を 3 通り検討した。すなわち Rust→RISC-V コンパイル (ベースライン)、Lean→RISC-V コンパイル、そして Lean→RISC-V のツールチェインを必要としない第三の 「IR Trace」 アプローチである。IR Trace アプローチではホスト側で Lean の lambda-RC (λRC) IR を *インタプリト* して実行トレースを記録し、zkVM ゲストは 各トレースステップを再検証する だけの小さなプログラムに縮める。実 ETH2 STF についてはホスト側のトレース生成こそ完走するものの、トレースが 8.14 GB (bincode シリアライズ後) に達して本実装で当たった入力パスの上限を超えるため、ETH2 STF の ゲスト内実行・証明はまだ実現できていない。本投稿ではその数値と直面した壁を共有し、トレース圧縮の方向性 (および「インタプリト後検証」という設計自体が正しい形なのか) について フィードバックを募集したい。

> 用語に関する注: 以下で「ホストがトレースを生成した」と言う場合、ホスト上でトレース生成が完走したことを意味する。トレースが検証されたことを意味するわけではない。ETH2 についてはゲスト側の検証器がまだ走っていない。

本投稿で報告するすべての結果は、以下の 2 つの前提の上に立つ。後段の議論を読む前にここを押さえてほしい:

1. Lean ランタイムの忠実なポートではない。 ホスト側 IR インタプリタにおける値モデル、stack/frame モデル、native/extern dispatch は、本ワークロード向けに Lean 意味論を 近似 した Rust 再実装であり、Lean 自身のランタイムではない。したがって本投稿で「Lean プログラムを実行した」と言う場合、それは「Lean の lambda-RC IR をこの近似ランタイムで実行した」という意味であり、Lean ネイティブランタイムとの bit-for-bit 等価性は確立していない。
2. 暗号は extern スタブとして公理化される。 `hashTreeRoot`, `blsVerify` 等は記録された結果を guest 側で受け入れ、再実行しない (詳細は次の「ゲストが実際に検査するもの」)。これらが本プロトタイプの信頼境界となる。

## 動機

そもそもイーサリアムのロードマップでは、コンセンサスレイヤの 状態遷移関数 (STF) を zkVM 上で証明可能にする 方向が議論されている。バリデータやライトクライアントが STF を毎回再実行する代わりに簡潔な ZK 証明だけを検証できれば、ノードのリソース要件は大きく下がり、コンセンサス参加の敷居も低くなる。本投稿はその文脈で、「STF をどう書き、どう zkVM に載せるか」の設計空間を探る試みである。

Ethereum コンセンサス仕様は、まさに証明支援系で書きたくなる類の成果物だ: 厳密な意味論、機械検証可能な不変条件。Lean 4 はそれに向いている。私たちが出発点にした問いは: STF が Lean で書かれているとして、ある pre-state + block から ある post-state が得られたことの簡潔な証明をどう得るか？

素直なルートは、その STF を zkVM 内部で走らせることだ。Lean 4 のコンパイラは関数型プログラムを最終的に C ソースコードに出力する ことができる (`lean -c` で `.c` を生成し、Lean ランタイムとリンクして実行ファイルにする)。したがって理論上は、その C を RISC-V 向けに再コンパイルし、Lean ランタイムの C ABI を FFI 経由で呼び出す ことで、zkVM のゲストプログラムとして走らせる経路が成立する。実装としてはまず Lean→C→RISC-V でクロスコンパイルし、ゲスト ELF が `lean_initialize`, `lean_io_mark_end_initialization` 等のランタイムエントリを FFI で叩いて STF を起動する、という構造になる。これは確かに動くが重く、Lean ランタイムと `Init` だけで本ベンチマークでは ~15M cycles の初期化コストを支払う。もう一方の選択肢として STF を zkVM 向きの言語で再実装する道もあるが、こちらは Lean 仕様とのリンクを失う。

そこで考えたのが: Lean を RISC-V にコンパイルすること自体を回避できないか？ Lean のコンパイラは C を吐く前に、プログラムを小さな IR (lambda-RC, λRC) に降ろしている。この IR は ステップ単位で逐次評価できる 構造を持つ — `let x := expr; ...` の連なりと、`Branch` / `Call` / `Set` 等の基本演算で構成されており、各ステップが「直前までの値テーブルから新しい値を 1 つ生成する」という形に整っている。これは zkVM の基本的な証明フロー、すなわち 「ステップ列を 1 つずつ再実行/再検査して、最終状態へのハッシュ的コミットメントを得る」 という枠組みと自然に噛み合う。ならば IR を *ホスト側で* インタプリトし、各ステップを構造化された実行トレースとして emit し、zkVM ゲストを言語ランタイム全体ではなく小さな トレースチェッカ に縮められないか? それが IR Trace アプローチである。

## 3 つのアプローチ

| アプローチ | ゲスト内部で動くもの |
|----------|------------------------|
| Rust コンパイル → RISC-V | 手書きの Rust 製 STF (ベースライン) |
| Lean コンパイル → RISC-V | STF 全体 + Lean ランタイム + `Init` (初期化だけで ~15M cycles) |
| IR Trace (本投稿の焦点) | ホストが生成した実行トレースを再検証する小さなチェッカ |

IR Trace のパイプラインは一方向である:

```
Lean 4 STF
   │  lambda-RC IR をダンプ  →  ir_program.json
   ▼
ホスト側インタプリタ  ──  入力上で IR をインタプリトし、各ステップを記録  →  trace (bincode)
   ▼
ホスト側ドライバ  ──  IR と入力をハッシュし、{ir_hash, input, trace} を zkVM に渡す
   ▼
zkVM ゲスト  ──  各トレースステップを再検証し、出力ハッシュを commit する
```

## ゲストが実際に検査するもの

トレースは平坦な 値テーブル (インデックスで参照される全中間値) と ステップ のリストから成り、IR プログラム・入力・出力の SHA-256 ハッシュを保持するヘッダで包まれている。何かを信頼する前に、ゲストはこの 3 つのハッシュが一致することを assert し、証明を特定のプログラム + 入力 + 出力に束縛する。

検証器は以下のようにトレースステップを再検査する:

- 値テーブルに対して完全に再検査されるもの: `PrimResult` (プリミティブ演算), `CtorCreate` (コンストラクタセル), `ProjResult` (フィールド射影), `SetResult` (フィールド更新の `Set` 演算), `Branch` (選択されたコンストラクタタグが scrutinee と一致すること)。
- 関数呼び出しはブラックボックスとして信頼しない: ユーザ関数の `Call` はトレースにインライン化されたサブステップで表現され、それら自体が検査される (下記の in-place ミューテーションのギャップあり — そのため留保なく「健全 (sound)」とは呼ばないようにしている)。
- 暗号系の extern スタブは公理として信頼される: `hashTreeRoot`, `blsVerify` 等は記録された結果を受け入れ、再実行しない (「このプロトタイプのスコープ」の前提 2 と同じ境界)。

現在の被覆ギャップ — in-place ミューテーション: ここは誇張しないよう注意してほしい。フィールド更新の `Set` 演算は再検査される `SetResult` ステップを emit する。しかし in-place ミューテーション演算 `USet` / `SSet` / `SetTag` は インタプリタで実行されるがトレースステップを emit しない。つまり現在は検証集合の 外側に落ちる。ETH2 の証明に意味を持たせるには、このギャップを塞ぐことが必須である。

何が正確に証明されているか: 証明は IR プログラムハッシュ、入力ハッシュ、出力ハッシュ、そして上記で検査されたトレース意味論を束縛する。Lean 自身のランタイムとの等価性は 確立しないし、スタブされた暗号の正しさも 確立しない。信頼境界は extern スタブの集合と上記の in-place ミューテーション被覆ギャップで尽きる。

## ベンチマーク結果

最初にカベアットを 1 つ: 3 つのアプローチは共通のコスト指標を持たない。直接比較できるのは *ワークロード* と *出力* のみで、zkVM cycle はコンパイル系の 2 つにしか存在せず、ホストインタプリタ統計は IR Trace にしか存在しない。そのため、誤解を招く 1 つの表ではなく、3 つのバケットで報告する。

### 1. 共通軸 — ワークロードと出力サイズ (3 つすべて)

3 つとも 同じ Lean 仕様の ETH2 STF を同じ入力上で 走らせる (N=10 と N=100 のバリデータ数)。直接比較できる *結果* はシリアライズ後の出力サイズだけである:

| 出力サイズ | N=10 | N=100 |
|-------------|------|-------|
| Rust (コンパイル) | 78,746 B | 91,976 B |
| Lean (コンパイル) | 78,746 B | 91,976 B |
| IR Trace | 78,522 B | 91,752 B |

IR Trace は両方の N で 224 バイト小さい。これはインタプリタを駆動するテスト入力シリアライザがコンパイル済みゲストのものと異なるためであり、STF 自身の発散ではないと考えているが、未調整であることをフラグとして示しておく。

### 2. コンパイル系のみ — zkVM コスト

zkVM cycle 数と segment は コンパイル系 2 つにのみ 存在する。IR Trace の ETH2 zkVM 検証は N/A — トレースサイズによってブロックされている (下記「壁」参照)。したがって ETH2 で IR Trace の cycle 値と「同一条件比較」できる数字は存在しない。その欠落を「速い」と読み替えないでほしい。

| アプローチ | N=10 cycles | N=10 seg | N=100 cycles | N=100 seg |
|----------|-------------|----------|--------------|-----------|
| Rust (コンパイル, ベースライン) | 12,491,509 | 13 | 14,446,747 | 15 |
| Lean (コンパイル, `Init` 込み) | 26,148,291 | 29 | 35,281,299 | 38 |

![zkVM cycles: コンパイル済み Lean vs Rust (N=10, N=100)。Rust はおおよそ Lean の半分の cycle 数。IR Trace の zkVM 検証はトレースサイズによってブロックされており利用不可。](assets/bench-zkvm-cycles.svg)

## 壁: トレースサイズ

ETH2 STF はホスト上でトレースを生成するが、サイズは 8.14 GB (bincode シリアライズ後), 639,836 の値テーブル要素を持つ。これをゲストに渡すことはできない: 本実装の入力パスは `env::write()` を介して `Vec<u8>` を u32 長さ prefix 付きでシリアライズしており、ホスト側で ~4 GB のあたりで `TryFromIntError` に当たる。

> これは 本実装で観測された入力パス上の制約 として述べているのであり、RISC Zero 仕様上の権威的な数字として述べているわけではない。

![対数スケールでのトレースサイズ: ETH2 STF のトレースは 8.14 GB で zkVM 入力上限の ~4 GB を超えている。](assets/bench-trace-size-wall.svg)

なぜトレースがこれほど大きくなるのか? インタプリタは すべての中間値 を値テーブルにクローンする。そして ETH2 の中間値には大きな `ByteArray` (beacon state は ~78 KB) と深くネストされた `Object` が含まれ、それらの多くが near-duplicate (例えば 1 インデックスだけ変更されたバイト配列が完全な新しいコピーになる) である。トレース形式を JSON (~15 GB) から bincode (8.14 GB) に切り替えても ~1.8× しか縮まなかった。これは、コストが JSON 構文オーバヘッドではなく、複雑なネスト値のシリアライズに支配されているからだ。

コンパイル Lean との対比: そちらでは中間値はページングされた zkVM メモリ上に存在し、決してシリアライズされない。IR Trace はすべての計算をホスト側に外部化し、すべての中間結果をゲストに手渡さなければならない — これが正に爆発の原因である。
